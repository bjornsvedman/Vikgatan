# Plan: Local Receipt and Invoice Manager

Build a local-first receipt and invoice manager with a .NET 10 LTS Minimal API, React + TypeScript frontend using Vite, PostgreSQL/pgvector, and Microsoft Foundry for document extraction and answers, pending confirmation of available models and approvals. The first version focuses on reliable ingestion, human review of extracted values, structured and semantic search, and answers cited to source documents. Defer OneDrive and automatic file watching.

## Steps

1. **Foundation:** Create the .NET 10 API, Vite frontend, and Docker Compose PostgreSQL service with pgvector and persistent storage. Confirm which Foundry models are available, whether they can be deployed, and whether their use is approved for the document data. Check region, quota, and embedding model availability. Separately check the Azure credits and entitlements included with the Visual Studio Professional subscription; optionally use an isolated Azure dev/test resource if Foundry is available there. Personal-subscription access does not imply Volvo approval. Do not send real receipts to it without authorization. Use the prescribed local authentication method, and define allowed document directories and upload limits.
2. **Data and application model:** Keep the application modular without adding distributed services. Store each document's ID, original filename, controlled storage path, content hash, document date, vendor, currency, total amount, category, description, extracted JSON, processing and review status, errors, and embedding model/version. Represent invoice line items explicitly. Add EF Core migrations and indexes for structured filters and duplicate detection. Use `Pgvector.EntityFrameworkCore` with a 1536-dimensional vector column, matching the measured embedding output; record the approved deployment/model version before generating embeddings.
3. **AI integration:** Define separate interfaces for document extraction, answer generation, and embeddings so providers can be replaced without assuming their APIs are interchangeable. The Microsoft Foundry Responses API extraction and Azure OpenAI embeddings adapters are implemented; extraction is opt-in, uses strict structured output, stores raw extraction JSON, generates a 1536-dimensional summary embedding, and leaves results in `NeedsReview`. Confirm the exact approved deployment names and data-use authorization before enabling any environment. Re-embed documents if the embedding model or dimensions change. Keep Gemini as an alternative only if separately approved and useful.
4. **Ingestion and review:** Start with a manually triggered scan of a configured folder and/or single-document upload. Make scans a `POST` action, deduplicate using content hashes, and track queued, processing, completed, failed, and review-needed states. Save extracted fields and line items, then provide an endpoint and UI for reviewing and editing them. Restrict file access to configured paths and validate file type and size. Defer a background watcher until there is a demonstrated need.
5. **Retrieval and cited answers:** The Q&A slice classifies questions into exact totals or semantic retrieval. Exact totals use PostgreSQL aggregation over reviewed receipts with optional year/vendor/category filters, grouped by currency; semantic questions embed the query, retrieve up to eight similar receipts, and fill remaining context with recent receipts when the archive is small or partially embedded. Foundry answers are constrained to retrieved records and source IDs are validated before citations are shown. Keep totals authoritative in SQL, never model arithmetic. Serve files through the ID-based endpoint that resolves paths under the configured document directory.
6. **Frontend and streaming:** Build the Vite UI with a query/chat view, cited document results and thumbnails, and ingestion and review views. For queries sent as `POST`, stream responses with `fetch`; browser `EventSource` only supports `GET`. Define cancellation, error, and completion behavior. Keep the frontend as a local-focused SPA; server-side rendering is not needed for the current scope.
7. **Testing and evaluation:** Test extraction validation, idempotent ingestion, storage-path containment, structured filters and aggregates, and citations. Create a small synthetic golden dataset with expected document IDs and exact-value answers. Measure retrieval Recall@K separately from answer correctness and latency.
8. **Numerical trust safeguards (future):** Ensure every authoritative number comes from a human-reviewed database field or deterministic calculation with inspectable inputs. Show interpreted year/vendor/category filters and the reviewed-only scope beside each total. Provide an expandable calculation listing every contributing receipt and stored amount, including when summary citations are capped. Prevent semantic answers from presenting calculated totals and route numerical aggregation requests to structured calculations; citations alone do not verify numerical claims. Flag missing amounts and unreviewed receipts so partial totals cannot appear complete. Preserve human review of extracted numbers because correct SQL arithmetic cannot repair incorrect source values. Test misleading questions, incorrect routing or filters, mixed currencies, missing data, and reconciliation of displayed totals against their contributing records. These safeguards are planned, not yet implemented.
9. **Receipt archive browsing (implemented):** The Archive page at `/archive` and `GET /api/documents/archive` browse all stored receipts, including completed receipts, separately from the review workflow at `/review` and without AI calls. The home page at `/` focuses on natural-language Q&A; archive filters and receipt lists do not appear there. Client-side navigation supports direct links and browser history while preserving archive state between pages. Group by document year by default, newest year first, with undated receipts last. Sort within each year by category, document date, vendor, or stored amount in either direction. Amount sorting does not convert currencies. Combine year/date-range, category, vendor, currency, and review-status filters, with removable active filters, clear-all, and explicit undated/uncategorized choices. Show date, vendor, category, amount, currency, and review status. Details, line items, and original files are accessible while preserving filters and ordering. Database queries use stable ID tie-breakers and bounded pagination (25 receipts per UI page). PostgreSQL tests cover grouping, sorting, filters, validation, and pagination; post-approval editing is covered in the next step.
10. **Edit approved receipts (implemented):** Open a completed receipt from archive details using Edit receipt at `/archive/{id}/edit`, and correct metadata or line items using the existing review form and validation. Save changes explicitly preserves completed status and returns to the archive; Cancel discards the draft without writing. Preserve the receipt ID, original file, and content hash. Saved corrections update archive filtering and SQL-based totals while retaining archive filters and sorting, including when a corrected receipt no longer matches the active filter. Changed content invalidates its embedding and model metadata; unchanged normalized content retains its embedding. Editing does not call Foundry, re-extract, or automatically re-embed documents. Invalidated receipts remain accessible through structured queries and the bounded recent-receipt fallback, but vector matching excludes them until re-embedded; backfill remains deferred. PostgreSQL tests cover approved corrections, unchanged content, invalid edits, and metadata/line-item updates; browser checks cover save/cancel, errors, direct links, and filter preservation without modifying real receipt data.
11. **Deferred phase:** Add Microsoft Graph/OneDrive sync and change notifications after the local workflow is proven useful. Account for authentication, conflicts, and remote changes.

Start PostgreSQL, apply migrations, and confirm pgvector is available.
2. Ingest the same sample file twice and verify it creates only one record. Verify visible failures for malformed, unsupported, or oversized files.
3. Verify invalid or uncertain extracted fields require review and that edits persist.
4. Test exact filters and monetary aggregates independently from semantic search; verify citations map to source records.
5. Verify the image endpoint cannot serve files outside the configured document directory.
6. Run backend and frontend tests and builds; exercise streamed POST queries, cancellation, and errors in the browser.
7. Evaluate retrieval and answer quality separately, reporting Recall@K, exact-value correctness, and latency.
8. When implementing numerical trust safeguards, verify displayed filters match the calculation, every contribution can be inspected, missing or unreviewed data is disclosed, and semantic answers cannot bypass deterministic aggregation. Test misclassified and misleading questions as well as mixed-currency and incomplete-data cases.
9. When implementing archive browsing, verify completed and unreviewed receipts are accessible, default grouping uses document year with an undated group, and category sorting works in both directions. Test combined filters, uncategorized receipts, clearing filters, stable pagination, empty results, and preservation of browsing state after opening a receipt.

When implementing post-approval editing, verify a category correction persists after reload, keeps the receipt completed, and updates category filters and grouped totals without changing the original file or receipt ID. Test other metadata and line-item corrections, invalid input, cancellation without saving, and embedding refresh or invalidation after relevant changes.

## Decisions

- Use .NET 10 LTS rather than .NET 9, which is out of support as of November 2026.
- Keep Vite; this is a local SPA consuming a .NET API.
- Use relational queries for exact facts and totals, and pgvector for semantic recall.
- The tested embedding output is 1536 dimensions; the local database column is migrated to `vector(1536)`. Confirm and record the approved embedding deployment/model before production use.
- Receipt extraction is disabled in committed defaults. Local extraction runs only when enabled through User Secrets; successful results remain unverified until a human marks them reviewed.
- Receipt Q&A supports bounded semantic retrieval with a small-corpus fallback, plus SQL-computed totals filtered/grouped by year, vendor, and category; totals are separated by currency and limited to reviewed receipts.
- Keep the first phase local and manually triggered. Defer OneDrive, watchers, and distributed infrastructure.
- Prefer Microsoft Foundry behind task-specific abstractions, pending confirmation of approved deployments, model capabilities, embeddings, quota, region, and data handling. Keep Gemini as an optional approved alternative.
- For streamed POST queries, use `fetch` rather than native browser `EventSource`.
- Keep the architecture modular and proportionate; avoid microservices and unnecessary framework layers.
